# Proof 23, a declaration that names the property, not the mechanism

## 1. The claim

`profile_requirements.isolation.declared` named a mechanism, `seatbelt`, and
every reader compared it by string equality. That was correct while one
backend existed. Slice 22's Landlock backend made it wrong in three places at
once, and none of the three is a cosmetic mismatch:

- **Availability.** `unavailable_requirements` compared `seatbelt` against
  what the host provides. A Linux host confining a run with Landlock ABI v4
  recorded `unavailable: ["isolation.declared"]` on `run.open` while being
  fully contained.
- **Refusal.** `on_unavailable: refuse` is the row the profile table says
  carries the weight, and it is what a `regulated` profile sets. Under a
  mechanism declaration, a regulated profile could not start on Linux at all,
  on a machine that confines it properly.
- **Scoring.** `config/scoring.json` required `tool.request./sandbox` to
  equal `seatbelt` for primitive 05 level 4. A fully confined Linux run scored
  3. The level was a statement about which operating system ran the workload.

The third is the one that matters most, because it contradicts the invariant
directly above it in `CLAUDE.md`: a scoring level credits a control running,
never what it found. It was crediting the control's brand name.

The tracked profiles now declare `per_run_confinement`: a per-run sandbox
holding both the filesystem and the network. Seatbelt provides it. Landlock
ABI v4 provides it. Nothing else does.

## 2. The attack

The obvious failure mode of naming a property is that it becomes a word for
"something ran". If every backend satisfied `per_run_confinement`, the field
would be decoration and the change would be a rename that quietly weakened a
control while appearing to generalise it.

So the question the change has to survive: is there a backend that provides
the mechanism and not the property, and does the code say no to it?

There is, and it is not hypothetical. Landlock added TCP bind and connect
restrictions in ABI v4. Kernels at v1, v2 and v3 enforce the filesystem half
and nothing about egress. `active_backend` already reported those separately
(`landlock-v1` through `-v4`) precisely so a kernel that enforces one half
could not be recorded as enforcing both, which is the distinction slice 22
built and this slice consumes.

The second question: does relaxing the comparison turn `gantry drift` into an
admission that agrees with itself? That is the exact defect `sandbox.egress_allow`
is reported `unobservable` for, and it is worth being suspicious of any change
that makes a drift field stop diverging.

## 3. What happened

### 3.1 The property is refused by a backend that holds half of it

`tests/profiles.rs::a_filesystem_only_backend_does_not_provide_confinement`
walks every backend string. `seatbelt` and `landlock-v4` provide the property.
`landlock-v1`, `-v2`, `-v3` and `none` are each a shortfall on
`isolation.declared`, and the shortfall names the backend actually in force,
so the reader is told the filesystem half is running rather than reading it as
no sandbox at all.

No such kernel was needed to check it. `unavailable_requirements` takes the
observed backend as an argument and reads no system state. That seam was built
in slice 17 so availability could not become a second observer, and it is what
makes every backend testable from a laptop that has one.

### 3.2 A mechanism declaration is not widened

The same test asserts the other direction: a profile declaring `seatbelt` is
satisfied by seatbelt and short on `landlock-v4`. A deployment that means one
specific sandbox still says so and still gets the stronger claim. The property
is an option, not a replacement.

### 3.3 The drift check had to be answered, not silenced

Running the gate after the policy change produced a real failure, and it was
the right one:

```
isolation: divergence (sandbox.active_backend)
  declared=per_run_confinement observed=seatbelt
```

Availability asks whether the machine could meet the declaration and holds a
set per field. Drift asks whether the one observed value agrees with the one
declared value, by string equality. The property broke the second reader.

`satisfies` in `src/drift.rs` answers it through the same
`sandbox::confines_filesystem_and_network` the availability side uses, and the
suspicion in section 2 is answered by where the observed value comes from: it
is read from the running kernel, and the question asked of it is whether that
backend holds both halves. Nothing derives the observation from the
declaration, which is what `sandbox.egress_allow` does and why that field
reports `unobservable` instead. `landlock-v3` still diverges, asserted in
`a_property_declaration_diverges_from_a_filesystem_only_backend`.

### 3.4 The scorer needed a matcher it did not have

The predicate vocabulary was `equals` and `present: true`. Neither expresses
"a sandbox was in force". `present` is not enough: `none` is present and
non-null, so it would credit an uncontained run with level 4.

`not_equals` was added. It requires the pointer to exist, be non-null, and
differ from the excluded value. Absent counts as not matching, deliberately: a
`tool.request` with no sandbox field is not evidence that a sandbox ran, and
reading absence as "differs from none" would hand level 4 to any producer that
stopped recording one. `a_sandbox_scores_by_being_in_force_and_not_by_its_name`
asserts both non-matching cases alongside the two that score.

### 3.5 Guides that had gone false

The change surfaced four documents still describing a one-backend build:
`README.md` twice in the self-score table and twice in prose, `docs/GLOSSARY.md`
in the sandbox entry and in the profile-availability paragraph, and
`docs/POLICY-SCHEMA.md` in the shape block, the profile table and the
declared-but-not-built list. `README.md` claimed an isolation backend other
than seatbelt does not exist. All corrected.

## 4. What surprised you

The gate caught the drift divergence, and that is the second time in two
slices that the honest answer was to fix a check rather than to reach for the
policy. Changing `config/policy.json` back would have made the gate green in
one line and left primitive 05 scoring the operating system.

The other surprise is where the defect was cheapest to see: not in the
sandbox, which was correct, but in a scoring rule that had been right for
nineteen slices and became a platform assertion the moment a second platform
existed. The tracked scoring rules are data, and the data went stale in a way
no Rust change could fail on.

## 5. Conformance delta

Primitive 05, execution environment: unchanged at 4 on macOS, and now reaching
4 on Linux, which it could not do at all. The number moved for the platform,
not for this machine.

Primitive 12, governance: `gantry drift` reports 3 match, 0 divergence, 6
unobservable on the tracked policy, the same as before the change. A profile
declaring a property it is given is not a divergence.

The static scan on this repository is unchanged at overall 0 against
telemetry's 3, and still reports 4 unenforced markers.

## 6. What is still a guide

- `per_run_confinement` is the only property the code understands. Every other
  declaration is compared as a literal, so `egress`, `identity`, `ledger` and
  `attestation` are mechanism names with the same brittleness this slice
  removed from one field.
- The v1 to v3 branch is unit-tested and has never run on such a kernel. What
  is proved is that the comparison refuses them, not that a v3 kernel behaves
  as the string says.
- `confines_filesystem_and_network` is a match on two strings. A third backend
  ships with a line to add here, and nothing fails if the line is forgotten:
  the new backend simply does not provide the property.
- `isolation.scores` is still read by no code, as `docs/POLICY-SCHEMA.md` has
  said since slice 17.
- The seatbelt egress allowlist is still generated from the policy's own
  `egress.allow` and still reports `unobservable`. Landlock scopes a TCP
  connect by port rather than by address, so the two backends do not even
  express the same allowlist, and nothing reconciles them because the tracked
  list is empty.
