# Proof 22, a console that answers for the workspace before it answers for a log

## 1. The claim

Two things, and the second is the one with a claim in it.

The console is redrawn to `docs/design/console-a-loadbearing.html`: paper
ground, condensed display type for structure, monospace for anything that came
off the record, and colour reserved for meaning. Hazard marks the primitives
holding the rail down; red marks a denial or a verification fault; a pass gets
no colour at all, so a clean board still cannot be produced by styling.
`assets/console.css` and `assets/index.html` are rewritten, and the nine views
are restyled through them rather than through markup changes, which is why the
eight assertions the render gate already held kept passing unmodified.

The claim is the workspace view. `gantry console` with no ledger directory now
lands on a page that reads `/api/projects`, `/api/projects/:id/scan` and
`/api/projects/:id/remediate`: a project index, the twelve primitives as a rail
chart resting on the minimum, the evidence behind every number, and the
remediation queue in the contracts' own words. The routes have existed since
`4b078a6`. Nothing rendered them.

Underneath it is one distinction the front end did not previously draw. A
console started without a ledger answers 404 on every ledger route. Before this
slice the boot path read any `/api/verify` failure as a verification failure
and took the interface over, so the first screen of a workspace console was a
red alarm about a log that does not exist. "There is no log here" and "the log
here is damaged" are different states, and only the second is an alarm.

## 2. The attack

Three questions.

First: can the workspace page show a static read as though it were telemetry?
The band above the ceiling is drawn from the `ceiling` the API returns, the
bars carry the scan's own scores, and the rail's label is the reported overall
rather than a number the browser computed from the bars.

Second: does the console rank the work itself? A front end that ordered the
remediation queue would be gantry prescribing a level, which is the one thing
this project refuses to do. The queue is rendered in the order
`/api/projects/:id/remediate` returns, and the check asserts the first heading
on screen against the first entry the CLI prints.

Third, and the one that had to be broken to be believed: does the no-ledger
path actually stay out of the verification takeover, and does every new
assertion die when the thing it names is removed?

## 3. What happened

### 3.1 The workspace reached the gate

`ci/console-render.sh` grows a third server: a workspace registry under
`$WORK/home`, this repository registered into it, and `gantry console` with no
ledger argument. Two routes render against it, `#/workspace` and `#/ledger`,
and every expected value is read from `gantry project scan` and
`gantry project remediate` at check time rather than written into the script.
The guard is the same one the ledger fixture has: a scan that yields other than
twelve primitives, no overall, nothing at the floor, or an empty first brief
fails the check before a browser starts, because assertions against an empty
extraction test nothing.

The check now reports nine views, four deep-linked routes, the takeover and a
ledgerless workspace.

### 3.2 Both new assertions were proved able to fail

`data-label="overall N"` renamed to `level N` in `assets/views.js`: the
workspace assertion died, naming the rail.

The 404 branch in `recordVerifyError` disabled, so a missing ledger is read as
an unverifiable one: the workspace assertion died first. That is a stronger
result than the one aimed for. The takeover renders instead of any view at all,
so the whole workspace assertion set sits downstream of the distinction, and no
part of it can pass while a console with no log presents itself as a console
with a broken one.

### 3.3 Two commands on the page were not commands

The design prototype ends its empty-chain panel with `gantry instrument
gantry`, and the first implementation of this view printed
`gantry project add <id> --ledger <dir>`. Neither exists. A console that prints
a command an operator cannot run is a guide that is wrong, which is worse than
a panel that says nothing. Both were replaced with `gantry console
<ledger-dir>`, which is real, and the panel now says what produces a ledger
rather than naming a flag that would produce one.

### 3.4 The page named two different targets for the same gap

The verdict said the primitives at the floor "have to reach 2" while the queue
beneath it said "raise from 0 to 3", both correct and together unreadable. A
static read awards no 1, so 2 is the next state this scan can reach; 3 is the
first level the contracts prescribe for. The verdict now says which number is
which and where each comes from, rather than picking one and being wrong for
the other reader.

## 4. What surprised you

The eight existing render assertions passed through a full stylesheet rewrite
untouched. That is not luck: they assert values that travelled from the ledger
through a fetch into the document, and one class name (`stat-v`) that a
selector-level change would have broken. A check written against rendered
values rather than against rendered appearance survives a redesign, and a check
written against appearance would have had to be rewritten line by line and
would have proved nothing new afterwards.

The reverse also showed up. `class="stat-v"` is asserted with its exact
attribute text, so any change that added a second class to that element would
have failed the gate. The stylesheet was written around that constraint rather
than the assertion being loosened, which is the correct direction.

## 5. Conformance delta

Primitive 11, observability: unchanged in score. The view renders an existing
read and adds no producer.

Primitive 12, governance: the console can be pointed at a set of repositories
with no ledger between them, which is the state every repository is in before
it is instrumented. The number it shows is a static one and the page draws the
ceiling it cannot pass, so the scan is not presentable as telemetry.

The static scan on this repository is unchanged at overall 0 against
telemetry's 3, and still reports 4 unenforced markers.

## 6. What is still a guide

- The workspace view reads on mount. A scan runs per request on the server, so
  a reload is current, and nothing polls.
- The chart is drawn for one project at a time. Comparing two means switching
  chips, and the index's twelve-tick profile is the only cross-project view.
- `nonAgentic` is a browser-side threshold of ten zero-scoring probes. It
  changes the words on the page and no number, but it is a judgement the API
  does not make and nothing checks it.
- A project row that cannot be read renders its fault and the other rows still
  draw. That path is not in the render gate: the fixture registers one readable
  project.
- The `--v` and `--min` custom properties carry scan values into CSS
  arithmetic. A score outside 0 to 5 would draw a bar out of its box, and
  nothing on the page clamps it; `ci/scan-evidence` refuses such a score at the
  source instead.
- The provenance bar's telemetry count reads `project.ledger` from the
  registry, which records that a ledger was declared and not that anything was
  ever written to it.
