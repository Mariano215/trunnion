# Proof 25, a deliverable a recipient can refuse

## 1. The claim

`docs/PLAN.md:11-23` named the proving workload on day one and twenty-four
slices went by without it: a sandboxed repository audit that emits "a signed
findings report where every finding carries an inclusion proof back to the
calls that produced it", bounded by `docs/CONCEPT.md` to secrets, dependency
provenance and authorisation boundaries. `docs/proof/24.md` section 6 recorded
what its absence cost: "Nothing feeds the ledger from a real coding session.
The operations view describes ledgers made by proof scripts and by hand."

This slice builds the missing half. `trunnion report` reads a sealed ledger and
writes a document in which every finding travels with an inclusion bundle for
the claim, for the read it rests on, and for the model call that produced it,
beside the public key those bundles check against. The workload that produces
one lives in a separate repository, `assay`, whose driver runs the same audit
six times adding one control per stage.

The claim under test is not that a document can be produced. It is that the
document **can be refuted by whoever receives it**, using the binary and
nothing else, and that it never says more than the log supports.

## 2. The adversarial case

A report is the surface where an agent system is most tempted to overstate,
because the reader is furthest from the evidence. Five attacks, all the same
shape: make the document say more than the record does.

**(a) A finding that is not a leaf.** If the claim lives beside the log, the
bundles can only ever cover its evidence, and the sentence a reader actually
acts on is unattested text the sender can edit after signing. `audit.finding`
is an event kind for exactly this reason, and `trunnion report` proves the
finding envelope itself, not only the events it cites.

**(b) A finding reusing `sensor.verdict`.** The lazy version of (a) is to write
the claim as a sensor verdict, which already exists and already scores. It
would have been wrong twice: that kind means a check with a fix and negative
controls ran, and a model assertion has none of those, so `trunnion score`
would have credited primitive 10 for prose. Nothing scores from
`audit.finding` at all: a claim is not a control, and a level that counted them
would pay for volume.

**(c) A finding about a file the run never read.** Observed live, twice, from a
0.6b model: a run reading `target/README.md` reported `class=secret
path=app/orders.py`, a file it had not been shown. The claim's own evidence
does not reach it. `fn audit` refuses any finding whose path is not the file
this run read, and the refusal names both paths. The first version of that
check compared the strings exactly and refused every finding a model wrote,
because a model shown an absolute path reports the tail of it; the rule is now
a suffix match, which still refuses the hallucinated file and stops refusing
the same file written shorter.

**(d) A file the policy refused, listed as a file the audit read.** The scope
section is what a reader uses to decide what was not covered. Building it from
`tool.request` alone lists every path the broker was *asked* for, including the
deploy key it denied, and the denial is two sections further down where nobody
correlates it. The list is built from requests whose result came back `ok`.
`a_refused_read_is_a_refusal_and_never_a_file_this_audit_read` drives a real
denial and asserts the scope reads `Files read: none` while the refusal section
names `r-credential-file`.

**(e) A proof that survives an edit.** The whole product in one test:
`a_claim_edited_after_the_fact_fails_rather_than_reading_as_verified` writes a
report, verifies a bundle, moves one character of the envelope's subject hash,
and asserts the same call now fails naming the entry.

## 3. What the run shows

Against the `assay` fixture with an 8b model on the local network, one file at
a time:

```
[broker] read .../target/app/orders.py, 855 bytes, tainted
[model] FINDING: class=authz.boundary path=.../target/app/orders.py line=10
        claim=The get_order endpoint allows retrieval of any order by ID without
        validating the user's association with that order record.
[broker] finding recorded as run-1786562514776-8: authz.boundary
[broker] 1 finding(s) recorded, 0 refused
```

The report that results carries the disclaimer above the findings, the verify
command under each one, and a section headed *what the harness refused during
this audit*:

```
- **deny** under `r-credential-file`. Reading a credential file is denied...
- **hold** under `r-publish`. This call gates pre at rung led for effect
  irreversible and needs an approval event before it can proceed...
```

That section is the only part of the document that is a fact rather than an
assertion, and it is free: the events were already there. The first is the beat
the workload was chosen for. The auditor finds the deploy key, reports it, and
then cannot read it back out, because the same policy that let it read the
source denies that path and the refusal names the rule.

Verification from a directory holding only the report:

```
$ cd report && trunnion ledger verify-inclusion proofs/f-1.finding.json ledger.pub
inclusion verified: entry 8 (id run-1786562636196-8) under signed head size 30
```

## 4. Two defects the workload found before it existed

Both were live for every user, and both are the reason a case study is worth
building rather than describing.

**The lifecycle sensor could not pass on any harness in existence.**
`templates/laptop/config/instruction-reviews.jsonl` was in the template and
never in the copy list `template_validate` returns, so `template init` wrote
the `instruction-lifecycle` sensor and not the file its check greps. The row it
did carry named `733b99a0…` while the template's own pack hashed to
`68933f15…`, which is what the template's policy correctly declared. So the
control failed on the first run of every harness, for a reason the operator did
not cause, and the usual answer to that is to switch the sensor off.

The fix is in the validator rather than the copy list: a template whose sensor
reads a review record must ship that record, and every pack it ships must have
a row. Proved able to fail by editing a pack without reviewing it, which is
exactly the drift that produced the defect, and by removing the record while
keeping the sensor. A template carrying neither is still accepted, because a
requirement with no control behind it would be a rule this file is not allowed
to add.

**`docs/proof/08-run.sh` claimed primitives 2 and 3 score N/A with the endpoint
down.** They do not. The error branch of `gateway::call_on` appends a
`model.call` carrying `prompt_hash` and `window` before returning the Fault, so
both score exactly as they do on a healthy call; what is lost is the reply, the
exit status and the seal. The comment had been wrong since slice 08 and is the
kind of false instruction this project's working agreement says is worse than a
missing one. Confirmed by pointing a provider at a closed port:

```
$ trunnion run providers.json local led
model call to local failed and is on the ledger: ... Connection refused
$ trunnion score led config/scoring.json
| 02 Context delivery | 3 | normalised model.call events with a pinned prompt hash |
| 03 Context management | 2 | window budget and actual recorded per call |
```

That is also what makes the assay ladder identical in CI, where no model
answers, and `ASSAY_OFFLINE=1` points the provider at a closed port so the
offline path is asserted on purpose rather than inherited from a runner image
that happens to have no model on it.

## 5. The ladder

Measured, not predicted. Each stage copies the previous log and adds one
control:

| stage | control | overall | scored |
|---|---|---|---|
| 0 | none, a static read of the target | 0 | 12 at zero |
| 1 | gateway and broker onto one signed log | 2 | 7 |
| 2 | a denial that names its rule, a drift walk | 2 | 7 |
| 3 | a sensor that trips, and one reported broken | 2 | 8 |
| 4 | a delegated sub-agent, a ledgered retrieval | 3 | 10 |
| 5 | durability, earned autonomy, a human gate | 3 | 12 |

Stages 2 and 3 add real controls and move the overall not at all, because
primitive 3 sits at 2 and the overall is the minimum. That is the arithmetic
`docs/CONCEPT.md` sells, and a case study that hid it would be selling
something else. The planning estimate for stage 3 was nine scored primitives;
it is eight, and the table records what ran.

## 6. What this does not do

- **It does not make a finding true.** The document says so in its first
  paragraph rather than its footer. A proof shows which bytes were read, which
  model was asked, under which policy and pack, and that none of it changed. A
  reader who wants the finding checked reads the same lines the agent was
  shown, which is why claims are required to be checkable by a person.
- **It does not anchor.** On the laptop profile the key is software-held and
  the head is unanchored, so an inclusion proof catches an edit and does not
  catch a writer who rewrote its own log and re-signed. The report says that
  under *what this record is worth*, and prints the anchor when one exists.
- **It does not schedule anything.** `trunnion report` runs when a person runs
  it.
- **The findings vary run to run.** A 0.6b model on loopback frequently reports
  nothing, or reports it in a shape that is refused. The driver asserts nothing
  about model output, and a run with no findings produces a report saying the
  audit ran and asserted nothing, which is a different statement from an empty
  page.

## 7. Conformance delta

- Primitive 10 and 11 gain a producer that is a real workload rather than a
  proof script. No scoring rule changed, and no level moved as a result: the
  ladder's numbers come from controls running, exactly as before.
- `RunCore::append` returns the id of the event it wrote, so an event can cite
  another instead of a reader inferring the link from adjacency. That is the
  same rule the trace view is built on, applied to findings.
- The remaining gap: nothing in trunnion's own gate runs the assay ladder. It
  lives in a second repository with its own CI, pinned to a branch rather than
  a commit until this slice merges. Until that pin is a sha, the ladder in
  `assay/README.md` is a claim about whatever trunnion's main is that day.
